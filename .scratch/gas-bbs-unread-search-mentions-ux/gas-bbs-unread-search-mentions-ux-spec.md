# GAS BBS — 未讀標記／手機燈箱滑動／圖片排序／看板內搜尋／@提及通知

## Problem Statement

看板文章列表只能靠捲動找東西，使用者無法一眼看出哪幾篇是自己上次來訪之後新發的、哪幾篇已讀文章有新回覆，只能逐篇點開確認。手機版燈箱看多張圖時，只能關掉燈箱重新點縮圖才能看下一張，跟桌面版（已有鍵盤左右鍵切圖）體驗不對稱。文章一旦選好圖片，順序就固定了，選錯順序只能刪掉重加。看板文章一多，除了捲動完全沒有辦法定位到特定文章。使用者在文章或回覆裡被別人 @ 提到時，完全不會知道，除非剛好自己讀到那一串。

## Solution

1. 重用既有「看板新內容提示」（`lastSeenBoards`）的資料，把判斷粒度從「這個看板有沒有新東西」細到「哪幾篇文章是新的、哪幾篇已讀文章有新回覆」，前端純比對時間戳，不新增任何試算表讀取。
2. 手機燈箱加左右滑動手勢，重用桌面燈箱既有的 `navigateLightbox_` 切圖邏輯與既有的手勢方向慣例。
3. 三個圖片表單（桌面發文／手機發文／編輯文章）的縮圖各自加上「往前移／往後移」按鈕，純前端陣列重排，送出時沿用既有的圖片來源驗證路徑。
4. 新增看板內搜尋（標題＋內文＋回覆），範圍鎖定使用者目前所在看板，優先對前端已載入的資料做即時比對，只有在使用者主動要擴大到「更早、尚未載入」的文章時才觸發一次既有的分頁讀取。按 Enter／點搜尋鈕才觸發。
5. 發文或回覆時偵測 `@userId`，只要這個 userId 真實存在、而且他的角色對這個看板有讀取權限，就把一筆通知記錄寫進他自己那一列（Users 表新增一欄，JSON 陣列）。每次登入時，把這欄內容整批顯示給使用者看（一個小 modal，列出被提到的每一則、可以點擊直接跳過去），顯示完立刻清空，不管使用者有沒有點開來看。

## User Stories

1. As a 使用者, I want 進到一個以前來過的看板時，看到哪幾篇文章是我上次來訪之後新發的, so that 我不用逐篇點開才知道有沒有新東西
2. As a 使用者, I want 看到哪幾篇「我已經看過」的文章，之後有了新回覆, so that 我知道該回頭看哪些討論串
3. As a 第一次進某看板的使用者, I want 不要被整片「未讀」標記洗版, so that 舊看板的存量文章不會全部被誤標成新的
4. As a 使用者, I want 點開一篇未讀文章之後，這篇文章的未讀標記立刻消失, so that 標記能準確反映我讀過什麼
5. As a 手機使用者, I want 在燈箱裡左右滑動切換圖片, so that 不用關掉燈箱重新點縮圖
6. As a 手機使用者, I want 滑到第一張或最後一張時滑動沒有任何動作, so that 行為跟桌面鍵盤邊界一致，不會意外跳圖或造成困惑
7. As a 發文者, I want 在編輯文章、桌面發文、手機發文三個地方都能調整已選圖片的順序, so that 不用刪掉重加就能修正順序
8. As a 使用者, I want 用簡單的移動按鈕（不是拖曳手勢）調整圖片順序, so that 手機跟桌面操作方式完全一致，不會有觸控手勢衝突的風險
9. As a 使用者, I want 在目前看板內搜尋文章標題、內文跟回覆內容, so that 看板文章一多也能快速定位到我要找的內容
10. As a 使用者, I want 搜尋結果如果命中的是某則回覆，直接帶我到該回覆所屬的文章, so that 不用自己在文章裡再找一次
11. As a 使用者, I want 搜尋預設只涵蓋我已經瀏覽過的文章範圍，需要時再手動擴大到更早的文章, so that 大部分情況下搜尋是即時的、不用等伺服器
12. As a 使用者, I want 搜尋只在目前所在看板進行，不會搜到我沒有權限看的其他看板內容, so that 不會有权限外的資料外洩風險
13. As a 使用者, I want 打 Enter 或按搜尋鈕才觸發搜尋, so that 畫面不會在我打字打到一半時就一直跳動
14. As a 使用者, I want 在文章或回覆裡 @ 提到某個真實存在、而且對這個看板有讀取權限的使用者時，對方會收到通知, so that 我可以直接把訊息帶到特定的人
15. As a 使用者, I want @ 到不存在的 userId 或沒有讀取權限的人時，什麼事都不會發生, so that 不會有指向死路的通知、也不會意外洩漏看板存在與否
16. As a 被提及的使用者, I want 每次登入時看到一份「誰在哪篇文章提到我」的清單，可以直接點進去, so that 不用自己再去找
17. As a 被提及的使用者, I want 這份清單顯示過一次之後就清空（不管我有沒有點開看）, so that 通知不會一直重複出現、也不會無限累積
18. As a 使用者, I want @自己不會產生通知, so that 不會有無意義的自我通知

## Implementation Decisions

### 已讀/未讀（文章 + 回覆）
- `Code.js` 的 `getBoardsFromToken`：在既有回傳的每個看板物件上，多加一個欄位帶出該使用者這個看板的原始 `lastSeenBoards[boardId]` 時間戳（空字串代表沒來過）。這個值本來就已經在函式的記憶體裡（`getLastSeenBoards`／`getBoardNewContentStatus` 已經在用），純粹多回傳一個既有欄位，不新增任何 Sheets 讀取，也不改動 `boardActivity.js` 裡任何一個既有的、已經有測試涵蓋的函式。
- 前端（`Index.html`）：把這個時間戳跟 `boardBulkCache` 裡每篇文章的 `createdAt`、以及每篇文章底下每則回覆的 `createdAt` 比對：
  - 時間戳為空字串（從沒來過這個看板）→ 完全不顯示任何未讀標記（文章、回覆都不顯示），避免舊看板洗版。
  - 文章 `createdAt` 晚於時間戳 → 該文章視為「新文章」。
  - 文章本身不是新文章、但底下至少一則回覆的 `createdAt` 晚於時間戳 → 該文章視為「有新回覆」。文章本身是新文章時不重複標記回覆維度。
- 視覺呈現：文章列表每一列的標題前面，新文章顯示一個小型「N」字樣徽章；已讀文章有新回覆時，在既有的 💬 回覆數量前面顯示同樣的「N」徽章（例如「N💬12」）。密度高的 36px 單行版面裡，這個徽章字級可以縮小（約 0.65rem）以容納。
- 這個比對純粹是前端邏輯，不牽涉任何伺服器往返，因此點開一篇文章時直接在本地把該文章（及其回覆）的徽章移除即可，不需要呼叫 `markBoardSeenFromToken` 或任何其他伺服器函式來達成「開過就消失」。

### 手機燈箱滑動切圖
- 重用桌面版既有的 `navigateLightbox_(direction)`，燈箱的 overlay／圖片元素上新增 `touchstart`／`touchmove`／`touchend` 手勢偵測，判斷方式與既有的手機文章滑動（左滑=下一篇、右滑=上一篇）用同一套水平位移／垂直容許誤差門檻常數。
- 方向慣例：左滑＝下一張（等同鍵盤 →），右滑＝上一張（等同鍵盤 ←）。
- 邊界（第一張再右滑、最後一張再左滑）不做任何動畫或回饋，跟鍵盤邊界行為一致，直接不動作。
- 需處理 `touchend` 後瀏覽器補發的合成 `click` 事件，避免一次滑動手勢被誤判成「點擊背景關閉燈箱」；判斷方式與既有 swipe 手勢實作採同一套模式。

### 圖片排序
- `Index.html` 既有的 `renderImageListHtml(list, addFnName, removeFnName)` 是桌面發文、手機發文、編輯文章三個表單共用的縮圖渲染函式，這次新增一個 `moveFnName` 參數（或等效的回呼機制），讓每個縮圖多顯示「往前移」「往後移」兩個按鈕。
- 按鈕邏輯：純粹是對應那個表單自己的圖片陣列（`newArticleImageList`／`mobileNewArticleImageList`／`editImageList`）做 `array.splice`／交換相鄰元素後重新渲染，第一張的「往前移」與最後一張的「往後移」按鈕停用（`disabled`），比照現有分頁按鈕在邊界停用的模式。
- 不做真正的拖曳手勢（HTML5 native drag-and-drop 在行動裝置支援不佳，Pointer Events 自製拖曳則需額外處理跟頁面捲動手勢衝突）；按鈕方案在桌面／手機行為完全一致，沒有額外風險。
- 送出時（無論是新文章的 `postArticleFromForm` 或編輯文章的 `editArticleFromForm`）都是把重新排序後的陣列原封不動送出，完全沿用既有的 `resolveImageSlots`／session 上傳連結驗證流程，不需要改動任何後端驗證邏輯。

### 看板內搜尋
- 搜尋範圍固定為使用者目前所在看板（不做跨看板搜尋），這個範圍限制同時也是權限邊界——使用者只可能「目前在」自己有讀取權限的看板，不需要另外對搜尋結果做一次跨看板的權限過濾。
- 搜尋內容涵蓋文章標題、文章內文、以及該看板底下所有回覆的內容；比對到回覆時，結果直接連到該回覆所屬的文章（不做「跳到特定回覆」的錨點機制，範圍內沒有這個需求）。
- 資料來源優先順序：
  1. 優先對前端 `boardBulkCache[currentBoardId]` 裡已經載入的文章與回覆內容做即時字串比對（純前端運算，零額外試算表讀取）。
  2. 若這個看板還有 `hasMore`（還有更早、尚未載入的文章分頁）且使用者想擴大搜尋範圍，提供一個明確的操作（重用既有的 `loadMoreArticles(boardId)` 分頁機制）把更早的文章載入後一併納入比對，不會自動觸發。
- 觸發方式：按 Enter 或點搜尋按鈕才執行比對，不做即時邊打邊搜（雖然本地比對成本極低，但避免畫面在打字過程中一直跳動）。
- UI 位置：搜尋輸入框常駐在文章列表上方（跟現有分頁 bar 同一個區域），不做成彈出視窗。

### @提及通知
- **Schema**：`Users` 表新增第 11 欄 `pendingMentions`，JSON 陣列字串，空值標準表示法是 `'[]'`（比照 `imageUrls` 欄位的慣例，不是空字串），儲存的是「尚未在登入時顯示過」的通知，每筆包含足以連到目的地與呈現摘要所需的欄位（看板、文章、標題、提到我的人、時間）。
- **偵測時機**：只在文章／回覆真正送出成功的當下（`createArticleForRole`、`createReplyForRole`）解析內文中的 `@userId` 標記，語法是 `@` 後面接 4~20 個英數字或底線字元（與既有 `validateUserId` 的 userId 格式規則完全一致），純文字比對，不做自動完成、不做模糊比對。編輯文章（`editArticleFromForm`）不會重新掃描內容找新增的 @ 標記——這次只涵蓋「張貼」當下，編輯時新增的 @ 不觸發通知，避免要 diff 新舊內容判斷「這個 @ 是不是這次編輯才加的」。
- **有效性過濾**：偵測到的候選 userId 要同時滿足「這個 userId 真實存在」、「這個使用者的角色對這篇文章／回覆所在的看板有讀取權限」（重用 `boardAllowsRoleByIdFor_`／`getRolePermissionsFor_` 既有的角色權限查詢方式）才會真的寫入通知；不滿足的候選一律靜默略過，不報錯、不通知任何人。一篇文章／回覆可以同時 @ 多個有效對象，各自獨立寫入各自的 `pendingMentions` 欄位。作者 @ 自己不產生通知。
- **併發安全**：多個貼文者同時提到同一個使用者時，各自「讀出→附加一筆→寫回」`pendingMentions` 欄位存在讀取-修改-寫回的競態風險（跟前一輪抓到的連點重複送出屬於同一類問題）。寫入這一欄時，對「被提及使用者那一列」的讀取-修改-寫回段落包一層短暫的 `LockService` 鎖，鎖的範圍只到這個欄位的讀寫，不影響發文／回覆本身其他既有的鎖定行為。
- **清空與呈現時機**：併入既有 `login()` 函式的登入寫回——目前 `login()` 已經在密碼驗證通過後對同一列做一次 `loginCount`／`lastLoginAt` 的 `setValues`；這次額外對同一列的 `pendingMentions` 欄位做第二次、範圍更小的寫入（清空成 `'[]'`），維持既有「只寫真正變動的欄位、不動其他欄位」的原則，不合併成單一大範圍寫入。`login()` 回傳值需要把清空前讀到的那份 `pendingMentions` 內容一併帶出去，供前端顯示。
- **前端呈現**：登入成功後，若回傳的 `pendingMentions` 非空，彈出一個小型 modal，逐則列出「文章標題／看板名稱／提到我的人／時間」，每一則可點擊，點擊後關閉 modal 並導覽到該篇文章（重用既有的文章開啟／深連結機制）。提供一個「關閉」按鈕可以整批略過不點。若為空，不顯示任何東西、也不留任何常駐圖示。
- **不需要額外跳脫**：`pendingMentions` 整欄寫入的值永遠是 `JSON.stringify(...)` 後的字串，開頭一定是 `[`，不會觸發 Sheets 的公式注入風險（`escapeFormulaInjection` 保護的是欄位值本身以 `=`／`+`／`-`／`@` 開頭的情況），因此裡面內嵌的文章標題等使用者輸入內容不需要再另外跳脫。

## Testing Decisions

- 好的測試只驗證外部行為（輸入→輸出／輸入→試算表的最終狀態），不驗證實作細節（例如不斷言「呼叫了幾次 `getRange`」這種內部呼叫次數，除非該次數本身就是這次要保護的行為，例如「零新增讀取」這類效能承諾）。
- **有 Node 測試覆蓋的部分**：
  - `Code.js` 的 `getBoardsFromToken` 多回傳的欄位：延伸既有 `boardActivity.test.js` 的測試方式，確認回傳值裡包含正確的原始時間戳（含「從沒來過」回傳空字串的邊界情況）。
  - 新的 `mentions.js`（或等效新模組）：`@userId` 擷取邏輯（純字串輸入輸出，含「格式不合法的候選字串不擷取」「同一則內文重複提到同一人只算一次」等邊界情況）、有效性過濾邏輯（存在性、角色權限、排除自己，各自獨立測試，仿照 `postArticle.js`/`postReply.js` 既有依賴注入 `spreadsheet` 的測試方式）、`pendingMentions` 的附加/清空邏輯（比照 `updateLastSeenBoard` 的測試方式，純函式輸入輸出）。
  - `createArticleForRole`／`createReplyForRole` 整合面：延伸既有 `createArticleForRole.test.js`／`createReplyForRole.test.js`，確認送出含有效 `@userId` 的內容後，目標使用者那一列的 `pendingMentions` 確實被寫入；含無效/無權限/自我提及情境下確認完全不寫入。
  - `login.js` 的 `login()`：延伸既有 `login.test.js`，確認登入後 `pendingMentions` 被清空、且回傳值帶出清空前的內容；確認未變動的其他欄位（`lastSeenBoards`／`articleCount`／`replyCount`）在這次寫入後仍維持原值（沒有被意外覆蓋，因為清空是獨立的小範圍寫入，不是跟其他欄位合併成一次大範圍寫入）。
- **不進 Node 測試、只靠 `MANUAL_VERIFICATION.md` 人工驗證的部分**（比照既有 tickets 02／03／06 的先例，純 `Index.html` 前端邏輯、沒有對應的 seam）：
  - 未讀/已讀的前端時間戳比對與徽章顯示、點開即消失。
  - 手機燈箱滑動手勢。
  - 圖片排序按鈕（含邊界停用）。
  - 搜尋的前端比對邏輯、觸發方式、擴大範圍的互動。
  - 登入後的通知 modal 呈現與點擊導覽。

## Out of Scope

- 編輯文章時重新掃描新增的 @ 提及（只有張貼當下觸發）。
- 搜尋回覆內容時跳到該則回覆本身的錨點定位（目前只做到「跳到文章」）。
- 跨看板搜尋。
- @提及以外的其他通知管道（email、LINE 推播）——目前系統沒有這些管道所需要的身分對應資料，這次只做站內、登入時顯示一次的版本。
- 圖片真正的拖曳手勢（改採按鈕方案）。
- 已讀/未讀狀態跨裝置／跨分頁同步（沿用現有 `lastSeenBoards` 本來就有的「單一時間戳、非即時同步」限制，不特別處理）。
- `pendingMentions` 清單筆數上限／清理策略——正常使用量級下這欄不會累積到有意義的大小（每次登入就清空），這次不特別設計上限。

## Further Notes

- 這次 5 個項目分屬完全不同的使用者情境，彼此之間沒有資料或流程上的依賴關係，適合切成互相獨立、可以任意順序完成的 tracer-bullet tickets。
- 已讀/未讀（文章＋回覆兩個維度）在對話中原本分成兩題（Q3 新回覆維度是追加確認的），實作時建議兩個維度一次做完，不要拆成兩張票——兩者共用同一個時間戳來源跟同一套「開啟即消失」邏輯，拆開反而增加不必要的協調成本。
- @提及通知是這次唯一新增 Sheets schema（Users 第 11 欄）跟新增模組（`mentions.js`）的項目，複雜度明顯高於其他四項，切票時應該給它足夠獨立的範圍，不要跟其他項目混在同一張票裡。
